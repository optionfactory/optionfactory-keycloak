# Changelog

## 9.19

- [NEW] themes-bootstrap: a phone field annotated `kc-phone` in the user profile is rewritten to canonical E.164 on blur and on submit - separators dropped, `00` turned into `+`, and the annotation's value prepended when the number carries no international prefix (`"annotations": {"kc-phone": "+39"}`). It is the client-side companion of the `phonenumber` validator, which accepts only that form: convenience so the rule refuses almost nobody, never the rule itself, since the same attribute is written by the admin api and by provisioning where no browser runs
- [BRK] providers: the `phonenumber` validator accepts only the canonical E.164 form - `+`, country code, digits - and its `default-region` option is gone. A validator cannot rewrite what it validates, since keycloak hands it an immutable `Map.Entry`, so accepting `+39 335 1234567` stored the spaces and left every reader of the attribute normalizing defensively; refusing it makes the canonical form an invariant of the realm instead, one that holds for the admin api and provisioning too, where no login form runs. A national number no longer parses at all, which is what `default-region` existed for. The new `error-phone-number-not-canonical` carries the canonical form as its parameter, so the form tells the user what to write rather than just refusing; `allowed-types` is unchanged
- [BRK] themes-preview: `serve()` is gone. It served the very pages `generate()` had already rewritten to open from the file system, so it added an url and nothing else - at the cost of a hand-rolled static file server, its own path-traversal guard and a mime table, in a build-time tool. Open `target/<output>/index.html`; the `@Disabled` tests that called it can go

## 9.18

- [NEW] providers: `phonenumber`, a user profile validator backed by libphonenumber. International `+CC` numbers always parse, national formats need `default-region`, and `allowed-types` narrows the accepted `PhoneNumberType`s (default `MOBILE` and `FIXED_LINE_OR_MOBILE`). Blank values are skipped, so requiredness stays the user profile's business, and region and types are checked when the config is saved. Messages ship as `theme-resources`, so any login theme resolves them; the libphonenumber jar is `provided` because the image stages it into `providers/`
- [NEW] api-provisioning: `PUT`/`PATCH /provisioning/users` take an optional `password`, as clear text or as a hash made elsewhere (`algorithm`, `hashIterations`, `hash`, plus `salt` where the algorithm keeps one apart - bcrypt and the like carry their own and send none). Clear text is hashed with the realm's algorithm and cost but deliberately not measured against its password policy, so a migration can carry over a password the policy would refuse today
- [BRK] api-provisioning: `enabled` and `emailVerified` are required on `PUT /provisioning/users`. They were primitives, so a missing flag defaulted to false and disabled the user on a 204
- [FIX] idp-apple: the `user` form field, which the browser posts and nobody signs, overrode the email of the signature-verified id_token, and the address inherited the token's verified status. It is read for the name now, the one thing apple sends nowhere else
- [FIX] providers: `ResourceAuthenticator.enforceServiceAccountHasClientRole` authorized on the roles of the client's service account without checking who was calling, so any token issued to that client - a direct access grant for an ordinary user, say - passed a guard meant for the service account alone. It also read only directly assigned roles, denying a service account that holds the role through a group or a realm composite
- [FIX] authenticators: the impersonation swap removed the cookie's user session and let the flow re-create one under the same id, in the same transaction, where the create discards the pending removal - committing a session whose stored user no longer matched. It restarts the session in place now (`restartSession`, what `attachSession` itself uses for that case). A parameter carried without a valid session is audited as `IMPERSONATE_ERROR`, which the readme always promised and the code never emitted
- [FIX] authenticators: `opfa-verify-email-otp` bound its code to the user alone, so an address that changed while a code was outstanding could be marked verified by the code sent to the previous one; it attached itself to users with no address at all, pinning them as permanently pending and so unimpersonable; and it replaced the stored code before the mail was accepted, letting a transient smtp failure destroy a code the user already had
- [FIX] authenticators: `conditional-user-group` compared the configured value against the group's *name* while the console's picker stores its *path*, so the condition never matched - silently disabling the gated sub-flow, or running it for everyone when negated. It resolves the path, counts membership of any group below it, and refuses to invert a condition it cannot answer
- [FIX] ldap: `caching-group-ldap-mapper` reported every membership twice, since it writes to the database what the delegate already reports from ldap; revoked only memberships directly under the groups path, leaving nested ones behind when ldap dropped them; and at the realm root counted every group as its own, dropping purely local memberships on each sync - a configuration now refused outright
- [FIX] api-provisioning: patching any attribute wiped the user's first name, last name and email, because keycloak reports those among `getAttributes()` and a REPLACE patch listed them as removals. `provide` also ignored a changed `username`, and a rejected request committed whatever it had already written - a `BadRequestException` carrying an entity never reaches the handler that marks the transaction for rollback
- [FIX] api-provisioning: the inspection endpoints tell a page and a slice apart (only a slice fetches the row that answers "is there more"), re-ask the total from the first page where `count(*) over()` yields no row, scope the recursive group-path CTEs to the realm and to realm groups (organization groups were surfacing as paths), qualify the `id` filter on the membership query, and no longer overflow `limit + 1` at `Integer.MAX_VALUE`
- [FIX] providers: malformed input on the filtering apis answered 500 where 400 was meant - a sort expression of nothing but separators, an iso instant beyond epoch milliseconds, an absent body, a null value for a known filter. A window with no sort ran over an unordered scan, free to repeat a row on two pages or skip it, and now falls back to ordering by id. `Groups.provide` split paths with slash escaping always on while `Groups.search` followed the server setting, so a group created by path could not be found by it
- [FIX] online-access: the endpoints ignored `online-access--enabled` while the action-token handler honoured it, so the boot log said `disabled` with the api live and its tokens unredeemable. The calling client's id was also concatenated into the set of valid redirect uris, where an id is not a uri
- [FIX] email-sender: a malformed `allowed_cids.json` escaped as an `UncheckedIOException`, past the `EmailException` the spi declares, so a theme typo answered a password reset with a 500 and re-parsed on every send. It is logged and treated as an empty allowlist now, and cid matching is case insensitive on both sides
- [FIX] remoting: a multipart write that failed half way stranded every part stream, including the `FileInputStream` a caller cannot get back; no `connectionRequestTimeout` was set, so the wait for one of the pool's two connections per route was unbounded (2 minutes now, tunable); and an empty header parameter went out unquoted, which strict multipart parsers reject

## 9.17

- [NEW] authenticators: `opfa-impersonation`, a browser-flow authenticator (first `ALTERNATIVE`, bound to the target client) that swaps the operator's cookie-backed identity for a target user on `impersonate=<userId>` and restores it on `deimpersonate`: the operator comes from the identity cookie validated in-code, role-less or session-less attempts fall through to a normal login with an `IMPERSONATE_ERROR` event, targets are guarded (exists, enabled, not a service account, holders of the operator role are never impersonable, optional `forbiddenRole`, no pending required actions and a verified email, else a warning page with back navigation), the swap writes the native `IMPERSONATOR_ID`/`IMPERSONATOR_USERNAME` notes (built-in mappers and introspection `act.sub` for free) and removes the current session server-side (no orphans, no chained leftovers; an inline backchannel logout would delete the root authentication session the flow itself executes in, since the authorize endpoint re-creates it with the cookie user session's id), and `deimpersonate` re-validates the operator's role and enabled flag before restoring. the ambient-authority trade-off of a url-borne parameter is documented and accepted
- [NEW] authenticators: `opfa-verify-email-otp`, a required action replacing the built-in `VERIFY_EMAIL` where the magic link is a liability (mobile custom tabs: the link opens the default browser and the parked tab never resumes): the email carries a numeric code the user types into the still-open login tab. Codes are sha-256-hashed in the single-use object store, single-use, expire after `codeLifespanSeconds` (900), are invalidated after `maxAttempts` (5) failed submissions and resends are rate-limited by `resendCooldownSeconds` (30), with `codeLength` (6) rounding the config; a closed tab needs no recovery path, the action lives on the user so the next login re-prompts and accepts a still-valid code. The code protocol (hashed single-use codes in the single-use object store, attempts atomically claimed so the cap cannot be raced, putIfAbsent-claimed resend cooldown) is extracted into `otp.OtpCodes` for reuse by other one-time code flows
- [ENH] themes-preview: the gallery opens from the file system - `target/<output>/index.html` in a browser tab, no server. Module scripts are the one thing no browser loads from a `file://` origin, so they are rewritten as pages are generated: the import map goes (nothing is left to import), an importing script is dropped (the stock ones are behavioral - session polling, webauthn, passkeys - and a preview is a still), and a module-free one keeps running as a deferred classic script (the locale dropdown, the password toggle). The index's editor reaches its frames over `postMessage` - the one channel that crosses `file://` origins, where a parent cannot reach into them - through a listener injected into every page, which also blurs the page's own autofocus (the scroll guard the index used to do by hand, and cannot from `file://`); `localStorage` and the clipboard degrade instead of throwing where a `file://` origin refuses them. The `rfc4648` stub is gone with the modules that imported it, and `serve()` stays as a convenience for who prefers an url

## 9.14

- [ENH] themes-bootstrap: the card is tokenised - `--opfa-card-bg`, `-radius`, `-shadow`, `-max-width`, `-padding` and `-min-height`, all defaulting to today's stock look (transparent, square, 400px, 15px). Themes were restating those properties to give the card a surface; `--opfa-card-min-height` is also the knob for the pin above, since a card taller than its content puts its actions at the bottom. A theme that wants any of it on one viewport only declares the token inside its own media query
- [ENH] themes-bootstrap: `.btn-secondary` and `.btn-outline-secondary` (`kcButtonDefaultClass`/`kcButtonSecondaryClass`) are driven by `--opfa-secondary{,-contrast,-border,-hover,-active,-disabled}`, the way `.btn-primary` already was - bootstrap compiles those palettes as literal hexes too, so every theme wanting a branded secondary was restating twelve `--bs-btn-*`. The defaults are bootstrap's own grey and its own derivation, so a theme that sets nothing renders unchanged
- [ENH] themes-bootstrap: `--bs-body-bg` and `--bs-body-color` now derive from `--opfa-surface-bg` and `--opfa-body-color`, so a theme tinting its fields no longer reaches for bootstrap variables directly; `--opfa-social-bg` defaults to the surface colour. They are declared under `:root:not([data-bs-theme="dark"])` rather than a bare `:root`, which would out-specify bootstrap's own dark block and pin the theme to light
- [BRK] themes-bootstrap: the action row sits at the bottom of a card taller than its content at any width, not only on a phone: the stretch chain leaves the library, so a theme that gives `.keycloak-card` a `min-height` gets its actions pinned on a desktop too, and a flow no longer resizes its box between steps. The chain makes those containers flex, which does not collapse margins, so the gap above an action row grows by the row's own `padding-top` where the block above it has a bottom margin - 32px instead of 16px on eight stock pages, up to 64px on `login-oauth-grant`. A theme that wants the old spacing sets its own `padding-top` on `#kc-form-buttons`/`.form-actions`
- [FIX] themes-bootstrap: the recovery-codes page reads as a page now: the warning is patternfly markup, so `kcRecoveryCodesWarning` drops `d-flex` (title above its description rather than beside it), the `pficon` box that resolves to nothing is hidden and the `h4` title is 1rem/600 instead of 1.5rem; the codes are monospace with a muted index (`kcRecoveryCodesList` gains a hook class); and the print/download/copy row has room around it and reads as accent-coloured links that underline on hover
